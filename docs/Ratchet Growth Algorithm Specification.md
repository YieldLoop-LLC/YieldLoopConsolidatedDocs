# YieldLoop — Ratchet Growth Algorithm Specification  
Version: 1.0  
Status: Core Economic Engine  
Scope: Redemption Floor Progression per Epoch  

---

# 1. Purpose

This document defines the deterministic mechanism by which:

- Redemption_price_E increases over time
- Ratchet_pool_E is deployed
- Surplus is converted into permanent floor increases
- Liability remains fully covered

The ratchet must:

- Never decrease redemption price
- Never violate coverage invariants
- Operate deterministically
- Avoid over-acceleration
- Preserve long-term sustainability

---

# 2. Definitions

For epoch E:

LOOP_supply_E  
Redemption_pool_E  
Ratchet_pool_E  
Redemption_price_E  
Coverage_ratio_E  

Where:

Coverage_ratio_E = Redemption_pool_E / (LOOP_supply_E × Redemption_price_E)

Minimum invariant:

Coverage_ratio_E ≥ 1.0

---

# 3. Ratchet Trigger Condition

Ratchet may activate only when:

Coverage_ratio_E ≥ Trigger_threshold

Where:

Trigger_threshold = 1.05 (default)

This ensures a minimum 5% surplus buffer before increasing floor.

No ratchet execution permitted below threshold.

---

# 4. Ratchet Increment Rule

Two valid implementation models exist.

## Model A — Fixed Increment (Recommended)

Δ_price_E = Fixed_increment

Example:

Fixed_increment = 0.0025 USDT

When triggered:

Required_transfer = Δ_price_E × LOOP_supply_E

If Ratchet_pool_E ≥ Required_transfer:

    Transfer Required_transfer → Redemption_pool_E
    Redemption_price_E += Δ_price_E

Recalculate Coverage_ratio_E

Repeat only if threshold still satisfied.

---

## Model B — Surplus-Proportional Increment (Alternative)

Surplus_E = Redemption_pool_E - (LOOP_supply_E × Redemption_price_E)

Allowed_increment = Surplus_E / LOOP_supply_E

Δ_price_E = min(Allowed_increment, Max_increment_per_cycle)

Transfer corresponding funds from Ratchet_pool_E.

This model adapts automatically to surplus size.

More dynamic, slightly more complex.

---

# 5. Execution Frequency

Ratchet evaluation occurs:

- Once per calendar month
- After new LOOP minting
- Before redemption window opens

Prevents intra-month manipulation.

---

# 6. Ratchet Pool Accumulation

Ratchet_pool_E increases only from:

60% of performance fees generated by that same epoch.

No external capital injections.
No cross-epoch support.

Ratchet_pool_E cannot be negative.

---

# 7. Hard Caps & Safety Controls

To prevent runaway acceleration:

Max_floor_increase_per_month = configurable parameter

Example:

0.01 USDT per month cap

This ensures:

- Predictable growth
- No instability from unusually large profit spikes
- Smoother user expectations

---

# 8. Redemption Protection Rule

Before applying any ratchet:

Simulate post-ratchet Coverage_ratio_E.

If:

Coverage_ratio_E_post < 1.02

Abort ratchet increase.

This enforces a minimum 2% post-adjustment buffer.

System must fail-closed.

---

# 9. Zero-Profit Months

If epoch E generates no additional profit:

- Ratchet_pool_E remains unchanged
- Ratchet may still execute if prior surplus exists
- Redemption_price_E remains constant if threshold unmet

No artificial floor growth permitted.

---

# 10. Long-Term Behavior

As LOOP_supply_E decreases via redemptions:

Required_transfer per Δ_price decreases.

This creates a natural acceleration effect:

Older epochs with reduced supply ratchet faster.

This is intentional and structurally sustainable because:

- Liability shrinks as redemptions occur
- Ratchet pool accumulates from historical fees
- Floor progression becomes easier over time

---

# 11. Invariants

At all times:

1. Redemption_price_E is non-decreasing.
2. Coverage_ratio_E ≥ 1.0.
3. Ratchet_pool_E cannot be used across epochs.
4. Ratchet execution must not reduce Redemption_pool_E coverage below required buffer.

Any invariant breach halts ratchet execution.

---

# 12. Design Philosophy

The ratchet is not yield generation.

It is surplus allocation.

It converts realized profit and accumulated fees into:

Permanent increases in redemption value.

No promises.
No projections.
No exponential assumptions.

Only surplus converts to floor.
